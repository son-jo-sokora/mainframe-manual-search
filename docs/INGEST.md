# 資料の取り込み方針（読み込みと加工）

検索対象にするすべての資料にこの方針を当てる。対象は IBM のマニュアル類の PDF（z/OS、Db2 など製品は問わない）。
各項目に **[実装済]** / **[未実装・提案]** を付ける。未実装の項目は、決まったらコードに入れてこの印を更新する。

## 決定事項（2026-11-04）

- 取り込む資料は **PDF のみ**。z/OS 以外に Db2 などの製品の、同じ形式の IBM マニュアルを追加する。
- **製品名と版を分けて持つ。** 「z/OS の版」ではなく「その資料の製品の版」を記録する（例: PSF 4.8、Db2 13）。
- **同じ内容のファイルや、同じ資料の別の版も両方残す。** 重複は除かない。

## 1. 全体の考え方

- 取り込みは「**形式ごとの変換**」と「**共通の加工**」の2段に分ける。
  - 形式ごとの変換: 元ファイル → 共通の中間形式（2章）。今は PDF だけ。
  - 共通の加工: 中間形式 → チャンク → 全文検索索引・ベクトル（5〜6章）。
- 将来 PDF 以外を扱うときは、中間形式を出す変換を1つ書くだけにし、`build_index.py` 以降は変えない。
- 原本は変更しない。原本・中間形式・索引はリポジトリの外に置き、コミットしない。
- すべて手元で処理し、外部のサービスに資料を送らない。

## 2. 中間形式（コーパス）

PDF のディレクトリごとに `extract.py` を実行し、同じコーパスに追加していく。**[実装済]**

```
python extract.py <z/OSのPDFフォルダ> <コーパス>
python extract.py <Db2のPDFフォルダ>  <コーパス>     # 同じコーパスに追加される
```

| 出力 | 内容 |
|---|---|
| `text/<PDFフォルダ名>/<相対パス>.txt` | 抽出したテキスト。PDF 1つにつき1つ |
| `manifest.json` | 文書ごとのメタデータ（3章）。キーは `text/...txt`（`/` 区切り） |
| `failed.tsv` | 取り込めなかった、またはスキャンの疑いのある PDF とその理由（全フォルダ分） |
| `failed.json` | `failed.tsv` の元データ（フォルダごとに再実行しても消えないように持つ） |
| `overrides.tsv` | メタデータを手で直すファイル（3章）。無ければ説明付きの空ファイルが作られる |

- PDF フォルダ名が同じだと置き場所がぶつかる。フォルダ名は製品ごとに分ける（例: `zos-pdfs`、`db2-pdfs`）。
  別の場所にある同じ名前のフォルダを追加しようとすると、`extract.py` は何も上書きせずに止まる。**[実装済]**
- `overrides.tsv` は UTF-8（BOM 付きも可）で読み、読めなければ Shift-JIS として読む（メモ帳・Excel で編集してよい）。
  キーの区切りは `\` でも `/` でもよい。**[実装済]**

テキストファイルの規則 **[実装済]**:

- 文字コードは UTF-8、改行は LF のみ。書き込みはバイト列で行う（Windows のテキストモードで書くと改行が `\r\n` に変わり、行番号がずれる。初回実行で実際に起きた）。
- 各ページの先頭に `=== PAGE n ===` の行を置く。n は **PDF 上のページ番号**（ビューアの番号）で、印刷されたページ番号ではない。

## 3. メタデータ（manifest.json の1文書分）

| 項目 | 意味 |
|---|---|
| `product` | 製品名（例: `z/OS`、`Db2`、`Print Services Facility`）。推定できなければ null |
| `version` | **その製品の版**（例: `3.2`、`13`、`4.8`）。推定できなければ null |
| `form` | IBM の資料番号（例: `SA38-0665-70`、`G550-0432-07`） |
| `title` | 資料名（表紙の先頭から、版だけの行を除いて最大5行をつなげたもの） |
| `pages` / `chars` / `page_starts` | ページ数、文字数、各ページの区切り行の行番号 |
| `suspect_scan` | 1ページあたり100字未満なら true（スキャンの疑い） |
| `source` | 元の PDF のパス |
| `auto` | 推定した値そのもの。`version_from` に推定の出どころ（`edition` / `cover`）を持つ |
| `overridden` | `overrides.tsv` で上書きした項目名の一覧 |
| `extractor` | 抽出規則の版（7章） |

### 製品名と版の推定 **[実装済]**

上から順に試し、最初に取れたものを使う。

1. **版の宣言文**（2ページ目あたりの「This edition applies to …」）
   - `IBM z/OS 3.2 (5655-ZOS)` → z/OS 3.2
   - `Db2 13 for z/OS (product number …)` → Db2 13
   - `IBM Print Services Facility Version 4 Release 8 …` → Print Services Facility 4.8
   - `Version 1 Release 2 of IBM Encryption Facility for z/OS` → Encryption Facility 1.2
   - `IBM CICS Transaction Server for z/OS, Version 6 (product number …)` → CICS Transaction Server 6
   - `the following licensed programs: …` のように複数の製品を挙げる宣言文からは決めない（表紙で試す）
2. **表紙**: 製品名の行（1〜4行）のすぐ後に版だけの行（`3.2`、`Version 4.8`、`V04.07.00`）がある形。
   表紙の中の `… Version 2 Release 4 …`、`BatchPipes OS/390 V2R1`、`z/OS 3.2 Licensed …`、`Db2 13 for z/OS …` の形も見る。
3. どれも無ければ null（`overrides.tsv` で補う）。

製品名の表記はそろえる: 先頭の `IBM`・`Program Directory for`、末尾の `for z/OS`・`(略称)` を除く。
`z/OS Communications Server` など `z/OS ` で始まる構成要素は `z/OS` にまとめる。
50字・6語を超える、`:` を含むなど、表紙の行を丸ごと拾ったようなものは製品名として使わない。

**ファイル名の版（`_v3r2` など）は使わない。** これは同梱先の z/OS の版で、製品の版ではないため。
（例: `aokfa00_v2r3.pdf` と `aokfa00_v3r2.pdf` は同じ資料 G325-2634-40）

全414冊での結果（2026-11-04）: 宣言文から299冊、表紙から69冊を推定。46冊は推定できず（古い DCF・OGL のマニュアル、フォントの資料、ホワイトペーパーなど。表紙に版が無い）。
Db2 13（28冊）・IMS 15.6（23冊）・MQ 9.4（17冊）・CICS TS 6.x（61冊）を追加した結果（2026-11-04）:
Db2 23冊、IMS・MQ・CICS は全冊を推定（CICS のプログラム・ディレクトリ6冊などは overrides.tsv で補正）。
推定できなかったのは IRLM（IMS と Db2 共通）、SQL Reference for Cross-Platform Development、Spatial Support の3冊。
製品名の末尾の版（`… for z/OS 6.2`）は取り除く。

IBM Redbooks（2026-11-05、45冊）: `redbooks-pdfs` フォルダから同じ手順で取り込む。
- 名前に `redbook` を含む PDF フォルダの文書は、検索結果のラベルを「Redbook」にする（`hsearch.py` の `is_redbook`）。
  製品・版の推定は通常どおり行い、版の根拠の文として表示する（多くは古い版が対象）
- 書名は扉の「International Technical Support Organization」の次の行から取る（表紙の書名は画像のことが多い）。
  取れなかった4冊は overrides.tsv で補正

埋め込みモデル（2026-11-04）: multilingual-e5-base から **BAAI/bge-m3** に変更。
日本語の問い12個（意味検索のみ、母集団 3万6千チャンク、正解は語の条件で決めた目安）で、
上位10件に正解: e5-base 11/12（MRR 0.54）、e5-large 11/12（MRR 0.72）、bge-m3 12/12（MRR 0.71）。
速度は RTX 3060 Ti で e5-base 約220件/秒、bge-m3 約57件/秒（全62万チャンクで約3時間）。入力長は512トークンに制限。

### 手での補正（overrides.tsv） **[実装済]**

タブ区切りで `ファイル名か manifest のキー / product / version / form / title`。空欄の項目は推定のまま。

```
dsnm_v13.pdf	Db2	13
apsm800_v4r8.pdf		4.8		PSF Messages and Codes
```

- `extract.py` を実行するたびに、推定値に戻してから補正を当てる。行を消せば推定値に戻る。
- どの文書にも一致しない行は、実行時に警告する。
- 補正しただけなら PDF の再抽出は起きない（すぐ終わる）。その後 `build_index.py` で索引に反映する。ベクトルは本文が変わらないので、`embed_index.py` が前回の結果を写すだけで済む（7章）。

## 4. PDF の変換 **[実装済]**

- `pdftotext -enc UTF-8 -eol unix` で抽出し、改ページ（`\f`）でページに分ける。CR は LF に置き換える。
- 段組や表の位置を保ちたいときは `--layout` を付ける（効果は未検証）。
- 文字の少ない PDF（スキャン）は `failed.tsv` に載せる。OCR はまだ無い（全414冊中12冊。古い DCF・OGL のマニュアル）。**[OCR は未実装]**

## 5. 共通の加工（build_index.py）

- 空行が続くときは1行にまとめる。**[実装済]**
- 30字未満のページは捨てる（白紙・ロゴだけのページ）。**[実装済]**
- チャンクはページをまたがない。1ページが約1800字を超えたら、約1200字ずつに分け、前のチャンクと約200字重ねる。**[実装済]**
- 重複したファイル・同じ資料の別の版は**除かない**（決定事項）。検索結果に同じ内容が並ぶ場合は、製品・版の絞り込みで分ける。
- 検索の邪魔になるページを索引とベクトルから除く（テキストには残す）。初回実行で、目次・索引・16進ダンプが意味検索の上位を占めていた。**[未実装・提案]**
  - 目次: 「......... 数字」の行が多いページ
  - 索引: 末尾の「Index」の章
  - 16進ダンプ: 8桁の16進数の並びが大半を占めるページ
- 各ページのヘッダー・フッター（例: 「z/OS: z/OS JES2 Commands」とページ番号）を除く。**[未実装・提案]**

## 6. 索引と検索

- 全文検索: SQLite FTS5。`$ # @` を語の一部として扱う（`$HASP373` を1語にする）。**[実装済]**
- 意味検索: `intfloat/multilingual-e5-base`。本文に `passage: `、問いに `query: ` を付ける。**[実装済]**
  - 初回実行では日本語の問いの精度が足りなかった。別のモデル（e5-large、bge-m3 など）と比べる。**[未実装・提案]**
- 絞り込み: 製品名（部分一致）と版（完全一致）。Web 画面では「製品 版」の組み合わせを一覧から選ぶ。**[実装済]**
- 答えにならないチャンクを検索時に除く **[実装済]**（`hsearch.py` の `is_junk`。索引とベクトルからは消さないので、ベクトル化のやり直しは不要）
  - 意味検索と語の一致の一覧から、目次（点線 + ページ番号の行が3行以上）、索引（行の半分以上が「語 + ページ番号」）、
    英文の少ないもの（普通の英単語が3割未満: 16進ダンプ・ロケール表など）、符号化データ（証明書・base64 の語が5つ以上）を除く。
    識別子の一覧には使わない（そちらは「定義 → 見出し → 言及」の段で並べる）
  - 日本語が半分以上で識別子を含まない問いでは、語の一致の一覧の重みを 0.3 に下げる
    （日本語の問いに混じる英字はたいてい製品名で、それを含むだけのページを押し上げていた）
  - 確認（2026-11-04、全543冊、ハイブリッド検索）: 識別子9個の定義ページは全部1位。
    日本語の問い9個のうち、Db2 のロックのタイムアウト・MQ のチャネル・CICS の ASRA・REXX などは関連するページが上位に来た。
    一方「保護例外のアベンド」「IMS のオンライン再編成」「SMF の記録を止めたい」は外れた。
    同じ内容を英語の技術用語（S0C4 protection exception / HALDB online reorganization など）で検索すると当たる。
    日本語の問いの精度は埋め込みモデル（multilingual-e5-base）の限界が大きい → 別のモデルとの比較が次の課題
- 識別子の定義を先に出す **[実装済]**（`hsearch.py` の `definition_score`、`zsearch.py` の `is_definition`）
  - 識別子を含む問いでは、識別子を含むチャンクを最大2000件取り、「定義 → 見出し → 言及」の段に分けてから並べる。
    最終の順位も段を優先する（語の一致の一覧が、識別子に何度も触れているだけのページを押し上げるのを防ぐ）
  - 定義: 識別子だけの行（または行頭の識別子 + メッセージ本文）の後、30行以内に Explanation・System action などの見出しがある。
    書名に Messages / Codes を含む資料では、識別子だけの行の直後に説明の文が続くものも定義とする
    （System Codes は理由コードの一覧が長く、見出しが150行後になることがある）
  - 言及とみなすもの: 他の識別子と並んだ一覧（関連情報・変更点の章）、目次、直前の行が別の項目の見出し
    （Explanation・Problem determination など）、直前の行が「:」で終わる出力例、直前4行以内に「Related …」の見出し
  - 確認（2026-11-04、全543冊、全文検索のみ）: 9個の識別子（DSNT408I、CSQX209E、DFHAC2206、S0C4、$HASP373、
    IEF450I、ICH408I、CSFM012I、IEC161I）で、定義のページが1位だったのは 1件 → 8件。S0C4 は2位
    （1位は同じ System Codes の待機状態コードの 0C4）。正解のページは zsearch で前後を読んで決めた
- ヒットした文書の版の確認 **[実装済]**: Web 画面のページ表示、`hsearch.py q`、`zsearch.py find/page` に次を出す。
  - 版をどう判断したか（版の宣言文から / 表紙から / overrides.tsv で手で指定 / 推定できず）
  - 根拠の文（manifest の `auto.version_evidence`。例:「This edition applies to IBM z/OS 3.2 (5655-ZOS) …」）
  - 元の PDF のファイル名
  - 同じ資料の他の版: 資料番号の末尾（版の番号）を除いた部分が同じ文書（例: SC14-7509-60 と -70）。
    資料番号の無い文書（MQ・CICS・z/OS の一部）は、製品名が同じで、ファイル名から版の数字（`mq93`→`mq#`、`_v3r1`→`_#`）を
    除いた部分が同じ文書（`hsearch.family_key`）。どちらが新しいかは、資料番号があれば刷の番号、無ければ版で決める。
    Web 画面では「この版で検索」で、同じ問いをその版に絞って検索し直せる。
    資料番号が無い文書は、他の版を見つけられない。
- 版による違いの表示 **[実装済]**（`compare.py`。Web 画面のページ表示、`hsearch.py q --diff`、`hsearch.py diff`）
  - **他の版との比較**: 表示中のページに対応する箇所を他の版から探し、行単位の差分を出す。
    1. 他の版の中で、そのページと語の重なりが大きいページを全文検索で最大8件選ぶ（問いに識別子があれば、それを含むページを優先）
    2. 各候補とその前後1ページを合わせた範囲で、行の一致率が最も高いものを対応箇所とする
    3. 一致率が30%未満なら「対応箇所が見つからない」（その版に無い、または大きく書き換わった）
    - 柱（ページ番号付きのヘッダー・フッター）は比較から外す。どの行が柱かは文書ごとに学習する:
      ページの先頭2行・末尾3行にあり、数字が PDF のページ番号と同じ歩調で増える行（印刷ページ番号 = PDF ページ − 一定の差）。
      前付けのローマ数字の柱は、本文の柱と同じ文字部分を持つものを外す。
      固定のパターンでは外さない。「Descriptor code: 4」や表の数値だけの行のような本文を誤って外さないため
    - 著作権表示（© Copyright …）と商標記号（®™）も比較から外す
    - 一致率は、文書の5%以上のページに出る定型の行（Explanation、System action など）を除いて計算し、
      位置合わせもそれ以外の行で行う。定型の行に引っ張られて隣のページと突き合わせるのを防ぐため（差分には定型の行も出る）
    - 確認（2026-11-04）: 柱付きの合成 PDF 2版で、Routing code 2→11 と表の値 8→12 を検出し、柱の違いは無視した
  - **変更点の章**: 各版の「Summary of changes」の章（見出しから `Chapter 1.` まで）を読み、問いの識別子が
    どのリリースの何（新規・変更・削除）として挙がっているかを出す。この章を持たない資料には効かない。
  - 確認（2026-11-04、ICSF Messages の z/OS 3.1 版と 3.2 版）: CSFM012I は 3.2 で変更（FIPSMODE(140-3,HYBRID,…) の追加）
    という差分と変更点の章の記載が一致した。CSFM042I は 3.2 で新規、3.1 には対応箇所なしと出た。
  - 限界: 行単位の比較なので、PDF の改行位置が版で変わっただけでも差分として出る。表の比較は崩れやすい。
    段落の途中で語が1つ変わっただけでも、その行全体が差分になる。

## 7. 再処理のルール

- 抽出: 次がすべてそろっていればスキップする。**[実装済]**
  - 元 PDF のパス・大きさ・更新日時が、前回抽出したときに記録したもの（`source`・`pdf_size`・`pdf_mtime`）と同じ
    （「抽出結果より新しいか」では判定しない。zip から展開した PDF は元の古い日付を持つため、差し替えを見逃す）
  - manifest の `extractor` が `extract.py` の `EXTRACTOR_VERSION` と同じ
  - テキストファイルが存在する
- **抽出やメタデータ推定の規則を変えたら `EXTRACTOR_VERSION` を上げる。** 次の実行で全文書が抽出し直される。
- PDF を消した・移した場合、そのフォルダを再実行すると、該当する文書とテキストがコーパスから消える。**[実装済]**
- 索引・ベクトル: `build_index.py` は毎回すべて作り直す。前回のベクトルは消さずに `vectors.prev.*` に移す（チャンクの番号が変わるので検索には使わない）。**[実装済]**
  - `embed_index.py` は、本文が前回と同じチャンクのベクトルを `vectors.prev.*` から写し、新しいチャンクだけを計算する（本文のハッシュ `vectors.keys.npy` で照合）。資料を足しただけなら、足した分の時間しかかからない。**[実装済 2026-11-05]**
  - 写せるのは、前回のベクトル化が最後まで終わっていて、同じモデルで、`vectors.keys.npy` があるときだけ（この仕組みより前に作ったベクトルには無いので、最初の1回は全部計算する）。
- 埋め込みモデルや除外規則を変えたらベクトル化をやり直す。そのため規則を決めてから全体を流す。

## 8. 失敗の扱い **[実装済]**

- 抽出できなかったファイルと、スキャンの疑いのあるファイルは `failed.tsv` に「パス + 理由」で記録する。
- 処理全体は止めず、失敗したファイルだけを飛ばす。次の実行で再び試す。
- PDF 以外のファイル（`.htm`・画像・`.DS_Store` など）は読まない。
